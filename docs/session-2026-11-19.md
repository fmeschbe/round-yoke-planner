# Round Yoke Planner: session record

This is a consolidated summary of the conversation and implementation decisions,
not a verbatim transcript. Earlier conversation turns were summarized during
the session. The final work recorded here is the initial-stitch limit change
published on November 19, 2026.

## Application scope and roadmap

The application is a browser-only round-yoke knitting calculator, repeating
stitch-chart editor, and schematic annular preview. It uses TypeScript, Vite,
semantic HTML, and SVG, with a bounded raster preview for dense patterns.
There is no application backend or server-side plan storage.

The agreed roadmap has four phases:

1. Schematic calculator, stitch chart, palette, and preview.
2. Browser-local storage and JSON import/export.
3. Standalone printable HTML and browser Save as PDF.
4. Stitch ancestry and explicit increase techniques.

Phases 1–3 are implemented. Phase 4 is **parked at user request**; its ancestry
contract must be agreed before implementation. Gauge, physical tension, and
drape simulation remain outside scope. Dedicated PDF generation, Markdown
export, accounts, server synchronization, and undo/redo were not added.

The detailed specification and acceptance decisions remain in
[`implementation-plan.md`](implementation-plan.md).

## Storage, portability, and localization

Plans are saved manually to IndexedDB. Browser storage has sufficient capacity
for these plans, but it is tied to the browser profile and website origin.
Persistent-storage permission can reduce eviction risk; JSON backups remain
recommended. Clearing browser data or changing origin can make saved plans
unavailable.

Saved plans reopen automatically using the most recently saved entry.
JSON imports validate before replacing the editor and receive a fresh identity.
The import limit is 1 MiB. Saving and renaming use transactional storage writes;
failures preserve the editable plan.

English, German, and Norwegian Bokmål are supported. Browser detection chooses
an initial language, and manual selection is remembered when storage is
available. Switching languages preserves drafts, colors, and unsaved changes.

## Calculator and geometry decisions

Increase-point presets are 4, 8, 16, and 32, with 16 selected initially.
The default plan uses SI = 64 and SF = 160. Dependent dropdowns retain valid
choices or select the smallest valid option; edits apply only through
Calculate / Apply.

Initial stitches were originally offered in the range 16–100. The final change
in this session expands the range to **16–200**, retaining the requirement that
SI be divisible by the selected IP. Final-stitch choices remain reachable
values in 100–300. Imported values outside the guided presets can still be
retained for the current plan.

Every increase point adds two stitches. Increases occur every IP / 2 rounds,
including the final increase. SF must be at least SI, and SF − SI must be
divisible by 2 × IP. Charts are limited to 5,000 rectangular slots, including
blocked slots and optional plain rounds.

Geometry changes preserve colors by section round and real-stitch ordinal,
not by raw grid column or proportional position. The chart remains anchored
top-left, growing or shrinking on the right and bottom, except for initial
plain rounds. Lossless changes apply without confirmation. Changes that remove
colored stitches require confirmation of the exact loss count; cancellation
preserves the applied chart. Expanding later does not restore deleted colors.

Initial plain rounds use SI stitches, are inserted above the yoke, and are
removed from the top. Their colors stay anchored nearest the yoke boundary.
Final plain rounds use SF stitches and are appended or removed at the bottom.
Neither changes the increase cadence or increase-section round count.
The chart uses continuous global numbering with separate section labels.

## Plan management and printing

The header uses a floppy-disk save button and a print button. Saving an unnamed
plan opens a naming dialog; saving a named plan writes directly.

The hamburger menu has seven entries:

- New plan.
- New plan from JSON, using file selection or drag/drop.
- Load plan.
- Save as, creating an independent saved copy.
- Export current plan as JSON.
- Download printable HTML.
- Manage plans, supporting rename and confirmed deletion.

Replacing an unsaved plan requires confirmation. Export does not implicitly
save to IndexedDB.

Printable HTML is a standalone offline reading/printing document, not an import
format. It includes the schedule, palette, background, preview, and numbered
chart panels. Panels use 4 mm cells, at most 40 columns by 40 rounds, and
repeated labels. Browser printing supports portrait A4/US Letter and Save as
PDF without a dedicated PDF library.

## Preview orientation and editing tools

The preview originally appeared mirrored relative to the chart. Its angular
direction was reversed so bottom-centered sectors match the chart's left-to-
right order. Full circles begin at 12 o'clock and progress counterclockwise.
Vector rendering, raster lookup, increase markers, and printable previews use
the same orientation.

The chart and preview both have expanded viewport views, entered through a
top-right icon beside their indicators. Each moves the existing panel into a
native dialog rather than duplicating rendering state. Returning restores the
panel and focus; expansion does not dirty the plan.

Chart editing includes confirmed clear-all and rectangular selection/cut/copy/
paste. Selection may include blocked slots. Clipboard rows preserve real-stitch
order, skip blocked destination slots, and include uncolored stitches, which
clear corresponding destination colors. A partial paste asks for confirmation
of omitted colored stitches. Matching colors are reused, missing colors are
added, and palette overflow is rejected before mutation.

The clipboard is confined to the current tab, works across plans, and is not
stored or exported. Ctrl/Cmd X/C/V, mouse/touch selection, and Shift + arrows
are supported. The compact toolbar has vertical dividers; supporting
announcements remain accessible without consuming visible header space.

## Container delivery

The chosen publishing trigger is **a published GitHub Release**, not ordinary
pushes. Publishing an image does not deploy it. No release was created by this
session.

The implementation provides:

- A multi-stage Dockerfile: Node.js 24 LTS build, then unprivileged Nginx.
- Runtime UID/GID 101, HTTP port 8080, and a `/healthz` endpoint.
- Read-only execution with temporary `/tmp`, and no persistent plan volume.
- Revalidated HTML and long-lived caching for hashed assets.
- A SHA-pinned GitHub Actions workflow publishing Linux AMD64/ARM64 images to
  `ghcr.io/fmeschbe/round-yoke-planner`.
- Release/version and full-commit-SHA image tags, with `latest` only for releases
  not marked as prereleases.
- Authentication through `GITHUB_TOKEN` with contents-read/packages-write.

The first GHCR publication may require a one-time package visibility change
to Public. Production deployments should use explicit versions or digests and
retain a stable HTTPS origin so browser-local plans remain accessible.

Local verification used the existing Podman machine after Docker Desktop was
found unavailable. The Docker context and existing machine were not changed.
Both native ARM64 and emulated AMD64 images were built and exercised.

## Kubernetes, Helm, and Compose

`deployment/kubernetes.yaml` provides a Deployment and ClusterIP Service with
health probes, restricted runtime settings, resource limits, and memory-backed
temporary storage. Ingress/TLS and cluster deployment remain operator-owned.

`deployment/helm/round-yoke-planner` adds a local Helm chart with configurable
image repository/tag/digest, replicas, pull policy/secrets, resources, and
Service type/port. A digest takes precedence over a tag; the default tag comes
from the chart appVersion. Optional root-path Ingress uses an existing controller
and optionally an existing TLS secret. The chart is not published by the
container workflow.

Root `docker-compose.yml` builds locally by default and supports published-image
or digest overrides, configurable host binding/port, restricted runtime
settings, restart-unless-stopped, and an explicit health check.

Build, release, Docker/Podman, Kubernetes, Helm, and Compose usage is documented
in the repository README. Validation containers and task-owned images were
removed without stopping the existing Podman machine.

## Verification recorded during the session

Application development included unit and cross-browser acceptance checks,
production builds, desktop/mobile inspection, and printable-output inspection.
Before the final range change, the unit suite contained 71 cases.

Container validation covered both architectures, non-root/read-only execution,
health checks, static HTTP/MIME/cache behavior, and missing-path responses.
Chromium, Firefox, and WebKit each exercised painting, preview, IndexedDB
save/reload, and JSON export against both architectures. Workflow linting and
strict Kubernetes schema validation passed.

Helm linting, packaging, default/custom/Ingress/digest renders, schema validation,
and missing-required-input errors were checked. Compose was built and run
through Podman's API; health, runtime restrictions, HTTP, and browser persistence
were checked.

For the SI maximum increase to 200, five calculator unit tests, fifteen
calculator browser checks across the three engines, and the production build
passed. Calculator tests and the build also passed after rebasing onto newer
remote changes.
